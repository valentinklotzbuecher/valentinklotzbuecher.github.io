Coding agents with GitHub

Let an AI agent do the routine work in an R and Quarto project, with every change on its own branch for you to review.

A coding agent is an AI assistant that works inside your project rather than in a chat window. It reads your files, runs R and Quarto, changes code and text, and checks the result, for instance by rendering a report and reading the errors. Paired with Git and GitHub, every change it makes is recorded, and you can read it, discuss it, undo it or keep it.

This page describes how I work this way on this website, my teaching materials and research code, and how to set it up for a project like the one in R and Quarto: a short start.

What you need

  • A GitHub repository for your project. A repository is a project folder under version control: Git records every change with a message, and GitHub keeps a copy online where you can browse it, compare versions and review changes. Private repositories are free. If Git is new to you, Happy Git and GitHub for the useR explains the one-time setup, and from an RStudio project usethis::use_git() and usethis::use_github() do the rest.
  • A coding agent. I use Claude Code, from Anthropic. It runs in a terminal, in VS Code and JetBrains editors, in a desktop app, and in the browser at claude.ai/code, where each session runs in the cloud on a copy of your repository. OpenAI’s Codex and GitHub’s Copilot coding agent work along the same lines. These tools generally need a paid plan.

In the browser, the agent works in a cloud environment of its own and installs what it needs there, and your computer can be off. On your computer, it uses what you have installed. Either way, what the agent reads is sent to its provider, which matters for your data (see what stays with you).

The workflow

  1. Describe the project once, in a short file in the repository’s main folder that the agent reads at the start of every session (see the next section).
  2. Give one task per session, in plain words: the goal, who it is for, and what done looks like.
  3. Let the agent work on a branch. It makes its changes on a separate branch, renders and checks them, commits them with messages that say why, and pushes the branch to GitHub. Your main branch stays as it was.
  4. Review. Read the changes on GitHub, where a pull request shows every changed line; render the branch yourself; ask questions or for changes in the same session.
  5. Merge the branch into main when you are satisfied, and publish if the project is a report or a website.
  6. Update the instructions. When the agent gets something wrong twice, add a line to them, so the next session starts knowing it.

This page was written that way: in a cloud session with my website’s repository, on its own branch, and reviewed by me before it was merged.

A file of instructions

Claude Code reads a file called CLAUDE.md; Codex, Copilot and most other agents read AGENTS.md, a shared format. Keep it short and concrete: how to build and check the project, its conventions, and what to ask about first. For a thesis in R and Quarto it could start like this:

CLAUDE.md
# Project notes

Master's thesis on [topic]. Text in Quarto (.qmd files), analysis in R.

## Build and check
- `quarto render` builds the thesis as PDF and web version into _book/.
- Render after every change; fix all errors and warnings before committing.
- `Rscript R/01_clean.R` rebuilds the clean data from data/raw/.

## Conventions
- Paths relative to the project folder; never setwd().
- tidyverse style with the |> pipe; one numbered script per step in R/.
- No numbers typed into the text: use inline R.
- British English, short sentences.

## Data
- data/raw/ holds the original files: never change them, never commit them
  (they are listed in .gitignore).
- Never print individual records.

## Ask before
- changing the sample, a variable definition or a model;
- deleting files or rewriting Git history.

In Claude Code, the /init command drafts such a file from your repository; shorten the draft and add your own rules. Rules about the statistics belong here too. The instructions in the repository of my journal club talk, for example, say: “report both models and the fixed validation split. Do not select a model or split because it yields a stronger signal” (AGENTS.md).

To serve several agents from one file, write AGENTS.md and start CLAUDE.md with the line @AGENTS.md, which imports it (more).

Prompts that work

Write as you would to a capable research assistant who has not seen the project: the goal, the context, and how you will judge the result. Ask for a check at the end and for a short note on anything left undone. For example:

  • Turn analysis.R into a Quarto report, report.qmd, that renders to HTML and Word. Hide the code in the output, put the numbers in the text with inline R, and cross-reference the figures. Render both formats and fix any errors.
  • Add a Table 1 by treatment group with gtsummary and refer to it in the results section.
  • Set up my thesis from the template in the GitHub repository valentinklotzbuecher/ufr_thesis, with my name and title and three empty chapters: Introduction, Data, Results.
  • Review R/03_models.R for mistakes such as wrong variables, silently dropped missing values or factor coding. Don’t change anything; list what you find with line numbers.
  • Explain what R/02_merge.R does, step by step, for someone new to dplyr.

For a larger change, ask for a plan first and agree on it before any code is written. Keep tasks small: a session that does one thing is easier to review than one that does five.

What stays with you

  • The decisions. The research question, the analysis plan, the sample, the model and what the results mean. An agent will propose answers to all of them; they are yours to make and to defend.
  • The checking. Read every change before you merge it, and rerun the analysis yourself. Agents are fast and sound sure of themselves when they are wrong: they misread a variable, or make a failing check pass by loosening it.
  • The data. Keep identifiable personal data, such as patient data, out of the repository and out of the agent’s reach, and follow your institution’s rules. A line in CLAUDE.md is a request, not a lock. Where the real data cannot be shared, the agent can write and test the code on synthetic data with the same structure, and you run it on the real data yourself.
  • The rules on AI use. Universities, journals and employers have them. Check what applies, and say how you used AI: in a thesis, usually in the declaration of independent work.

In a study I co-authored, AI-assisted teams assessed the reproducibility of published research better than AI-led teams, but not better than human-only teams.
